# Stage E Mobile V1 — PHASE-5.5 Spike: Universal/App Links

Status: spike/audit only. No production code changed. No implementation merged.

Answers the readiness audit's own PHASE-5.5 entry
(`plan/STAGE-E-MOBILE-V1-PHASE-5-READINESS-AUDIT.md` §14) and the master blueprint's
Open Decision #2. Builds on, and does not repeat, the prior **E0.2** spike
(`plan/PROGRESS.md`, 2026-08-26) — E0.2 tested a *throwaway* app against a *throwaway*
domain; this spike re-tests the same question against **this repository's real,
merged PHASE-5.1–5.4 code**, which did not exist when E0.2 ran.

## 1. Current State

- **Custom URL scheme** (`timelycapsule://`) — configured in `apps/mobile/app.json`
  (`"scheme": "timelycapsule"`), the only linking configuration that exists in this
  repository today. Used throughout PHASE-5.1–5.4's own real-device verification.
- **Android App Links** (`https://` + `intentFilters` + `assetlinks.json`) — **not
  configured anywhere in this repo.** `apps/mobile/app.json`'s `android` block has no
  `intentFilters` key. No `assetlinks.json` exists anywhere in the repository
  (`find . -iname assetlinks.json` — zero results, checked directly this session).
- **iOS Universal Links** (`https://` + `associatedDomains` + `apple-app-site-association`)
  — **not configured anywhere in this repo.** `apps/mobile/app.json`'s `ios` block has no
  `associatedDomains` key. No `apple-app-site-association` file exists anywhere in the
  repository (same search, zero results).
- **Ordinary HTTPS web links** — fully functional today. The real recipient email
  (`apps/api/src/modules/recipients/service.ts`'s `sendRecipientLink` →
  `sendSomethingWaiting`) embeds a real link built as
  `${window.location.origin}/c/${accessToken}#${encodeCapsuleKeyForLink(capsuleKey)}`
  (`apps/web/src/lib/use-capsule-draft.ts`'s `sendAnnounceToAll`, read directly, not
  assumed) — in production, `https://timelycapsule.com/c/:token#k=...`. Every such link
  today opens in whatever the OS's default browser is, on both platforms, because
  nothing has ever told either OS the app can handle it.
- **Expo development/deep-link behavior** — `Linking.useLinkingURL()` (from `expo-linking`,
  used directly in `app/(reveal)/c/[token].tsx`'s `UnlockedReveal`) is the mechanism
  PHASE-5.2 actually shipped. Traced its real implementation
  (`apps/mobile/node_modules/expo-linking/build/Linking.js`): its initial state is
  `useState(ExpoLinking.getLinkingURL)` — a **synchronous** native getter call at first
  render — then a persistent `onURLReceived` listener for updates. This is a materially
  different (and newer) API than the `useURL()` hook E0.4's own spike diagnosed a
  warm-reopen race in (that one seeds its initial state from the *async*
  `getInitialURL()` promise, which can lose a race against navigation). `app/_layout.tsx`'s
  own comment ("Deliberately no deep-link URL capture here... no route in this ticket
  consumes a captured URL") is now stale prose, not a functional problem — PHASE-5.2 did
  ship a consumer, and it reads the URL directly in the leaf screen via the newer,
  synchronous-getter hook rather than the root-layout-capture workaround E0.4 needed for
  the older one. Confirmed by real-device testing (§8) that this actually works, not just
  inferred from the API shape.

app** (methodology and disposal in §12):

- A real HTTPS domain (`https://tc-p55-spike-8753.loca.lt`, a `localtunnel` tunnel — a
  real, trusted-cert HTTPS endpoint, matching E0.2's own "smallest isolated test domain"
  precedent) served a real `assetlinks.json` naming this repo's real
  `com.timelycapsule.app` package and this machine's real local debug-keystore SHA-256
  fingerprint.
- A temporary `android.intentFilters` block was added to `apps/mobile/app.json` (never
  committed — reverted before this spike's own commit; diff confirmed empty via
  `git diff apps/mobile/app.json` after revert), the app was rebuilt via
  `npx expo prebuild -p android` + `npx expo run:android` (the *existing* checked-out
  `android/` folder, generated by earlier PHASE-5.1/5.3 native builds, does **not**
  auto-regenerate from `app.json` on a plain `expo run:android` — prebuild must be
  re-run explicitly; this is itself a real, disclosed toolchain finding, not assumed).
- **Without explicit package targeting**, `adb shell am start -a VIEW -d
  https://tc-p55-spike-…/c/…` opened **Chrome**, not the app — reproducing E0.2's own
  finding exactly, now against this repo's real app rather than a throwaway one. No
  "Always" disambiguation had been recorded, so the OS defaulted to the browser — the
  expected, correct behavior for an unverified/undecided handler.
- **With explicit package targeting** (`-p com.timelycapsule.app`, simulating a user who
  already chose "Always" once — the same effective resolution App Links reach after
  successful verification), the real `https://` link — carrying a real
  `#k=...` fragment — was delivered to **this repo's actual Expo Router `(reveal)/c/
  [token].tsx`**, which:
  - extracted `token` from the real HTTPS path correctly,
  - called the real `GET /r/:token` against a real running `apps/api` + Postgres,
  - for a genuinely nonexistent token, rendered the real, correct "No capsule at this
    link." system state (masked-404, unchanged from every prior ticket's own testing);
  - for a real seeded capsule with a real `contentDocEnc` and a real fragment key, the
    `#k=...` fragment survived **byte-for-byte** through the whole chain
    (`Linking.useLinkingURL()` → `keyFromOpenedUrl` → `decryptRevealLetter` →
    `decryptField`/AES-GCM) and rendered the exact real plaintext ("A real Universal
    Link delivered this.") on screen, via the genuine reveal ceremony (confirmed
    mid-transit, with the "Show the letter now" skip control present, then at rest).
  - This is the first time this exact question has been answered against this
    repository's own merged code, on a real (if tunneled) HTTPS domain, rather than
    against a throwaway app.
- **Warm, already-running re-delivery**: the app was already mounted on the reveal route
  (for a different, nonexistent token) when the second, real-content `https://` link was
  delivered — it correctly replaced both the route param and the fragment and re-ran
  decryption from scratch. This is a genuine, positive, real-device answer to deep-link
  matrix case 1 (app already running → tap link) for Android, using `useLinkingURL()`
  specifically, not merely inferred from its synchronous-getter implementation.

## 3. What Does Not Work / Was Not Verified

- **Android App Link domain verification, for real**: `adb shell pm get-app-links`
  reported a verification state, but — following E0.2's own explicit warning not to
  trust that report at face value — the tunnel's own HTTP access log was checked
  directly and showed **zero requests from the device**; every logged fetch was from
  `::1` (this session's own `curl` calls). The device never actually fetched
  `assetlinks.json` over the tunnel during this spike, matching E0.2's identical finding
  on its own throwaway domain. This is a real, reproduced toolchain caveat: on this AVD
  image, whatever "verified" state Android reports is not by itself proof of a
  completed network check, on **any** domain tested so far, throwaway or real-ish.
- **Cold start after a fully killed process, on Android, via this session's tooling**:
  attempted directly (`am force-stop` then a real `https://` link tap). The result was
  the Expo dev-client's own "Development Build" launcher screen, not the app's JS layer
  — a **local debug dev-client build must reconnect to the Metro bundler before any JS
  routing code (including the deep-link consumer) is even alive**, and that reconnect
  visibly took several seconds and one retry in this run. This is a genuine, disclosed
  limitation of *this specific test rig* (an unbundled local debug build), not evidence
  about production cold-start behavior — a real EAS-built preview/release binary embeds
  its JS bundle and does not need a Metro connection to boot, so this exact failure mode
  would not occur there. It could not be verified either way with the tooling available
  this session (no EAS credentials, no built preview/release binary). **Genuinely
  NOT VERIFIED — disclosed, not assumed either way.**
- **iOS, entirely**: not attempted this session, for the same hard blockers E0.2 already
  established and re-confirmed present (no interactive iOS Simulator/device tooling
  exists in this environment at all, and even where it did, `associatedDomains`
  requires Xcode to resolve a real, signed-in Apple Developer Team, which this machine
  has never had — `security find-identity` returning none is unrelated to this session's
  own tooling limits and was E0.2's own finding, not re-derived here). Per this ticket's
  own explicit instruction not to claim iOS verification without a real, correctly
  configured domain and environment: **none is claimed.** iOS Universal Links remain
  exactly as E0.2 left them: UNTESTED, hard blocker, physical-device + real Apple
  Developer Team is the only way to close this.
- **Real production domain**: nothing in this spike touched `timelycapsule.com` itself —
  no DNS record was created, no file was ever hosted there, and no request was ever
  sent to it. Every finding above is on a temporary substitute domain, exactly matching
  E0.2's own "smallest isolated test domain" discipline. The production domain's own
  real hosting behavior remains unverified and depends entirely on the human/external
  work in §9.

## 4. Android App Links Requirements

- `apps/mobile/app.json`'s `android` block needs an `intentFilters` entry (proposed
  shape below, mirroring the experiment above but scoped to the real domain) —
  **proposed, not applied**:

  ```json
  "intentFilters": [
    {
      "action": "VIEW",
      "autoVerify": true,
      "data": [{ "scheme": "https", "host": "timelycapsule.com", "pathPrefix": "/c/" }],
      "category": ["BROWSABLE", "DEFAULT"]
    }
  ]
  ```

  `pathPrefix: "/c/"` is deliberate and load-bearing, not cosmetic: Android's own
  intent-filter `<data>` element supports path-scoped matching, and scoping to `/c/`
  specifically avoids the app claiming `timelycapsule.com`'s marketing site, `/login`,
  `/signup`, or any future page under the same domain (see §7).
- A real `assetlinks.json` hosted at `https://timelycapsule.com/.well-known/
  assetlinks.json`, naming `com.timelycapsule.app` and the **real production release
  signing certificate's** SHA-256 fingerprint — not the local debug fingerprint this
  spike used, which is unique to this machine's own debug keystore and meaningless for
  a real install.
- The real fingerprint does not exist yet: no `eas.json` exists in this repository
  (checked directly — absent), meaning no EAS build profile, and therefore no
  EAS-managed release keystore, has ever been created for this app.

## 5. iOS Universal Links Requirements

- `apps/mobile/app.json`'s `ios` block needs an `associatedDomains` entry, e.g.
  `["applinks:timelycapsule.com"]` — **proposed, not applied**, for the identical
  reason as Android (untestable without the domain files hosted, and this session has
  no iOS environment to test it in even if applied).
- A real `apple-app-site-association` file hosted at `https://timelycapsule.com/
  .well-known/apple-app-site-association` (no extension, served as `application/json`
  or without a content-type restriction depending on Apple's own current requirements),
  naming the real Team ID + bundle identifier (`com.timelycapsule.app`) and, like
  Android, scoped via its own `paths` array (e.g. `["/c/*"]`) to avoid claiming the
  whole domain.
- Requires a real, paid Apple Developer Program membership and a Team ID — confirmed
  absent from this environment (E0.2's own finding, re-confirmed: `security
  find-identity` returns no signing identities on this machine).
- Requires Associated Domains capability enabled on the app's App ID in the Apple
  Developer portal, and the corresponding entitlement in the iOS build.

## 6. Web Fallback Behavior

Already correct and already proven (E0.2's own empirical test, re-confirmed by this
session's direct reading of the same reveal page code — unchanged since): when a
`/c/:token#k=...` link is opened in an ordinary browser (app not installed, or App/
Universal Link not yet configured — today's actual, universal case), the web reveal
page handles it exactly as designed, with no fragment ever reaching a network request,
`localStorage`, or `sessionStorage`. **Nothing about adding App/Universal Links changes
or risks this path** — it is what already happens for 100% of real recipients today, and
remains what happens for anyone whose OS doesn't hand the link to the app (old phones,
Android's own default-browser choice, iOS users who've disabled Universal Links for
this app in Settings).

## 7. Security Analysis

Traced directly, not assumed, against this repo's real code:

- **Token exposure in logs**: none found. Full-session device logcat was grepped for
  the real seeded token, the real capsule-key fragment, and the real decrypted
  plaintext used in this spike's own experiment — zero hits (§12). This matches every
  prior PHASE-5.x ticket's own established discipline and is not a new risk App/
  Universal Links introduce: the OS hands the *whole URL, including its fragment* to
  the app via the exact same `Linking`/`onURLReceived` mechanism the custom scheme
  already uses — there is no new place for the token or key to leak that didn't already
  exist for `timelycapsule://`.
- **Token survival across navigation**: confirmed directly (§2) — the fragment survived
  intact through a real cold-to-warm delivery, route-param extraction, and decrypt.
- **Redirect/referrer leakage**: none possible. Neither the API (`GET /r/:token`) nor
  the web reveal page issues any redirect for this route (`apps/web/next.config.ts` has
  no `redirects()` entry at all, and no middleware exists — checked directly, both
  absent). An App/Universal Link handoff happens entirely at the OS level, before any
  HTTP request is made at all when the app intercepts it — there is no intermediate
  hop, and therefore no `Referer` header, involved.
- **Fragment/query/path preservation**: path (`token`) and fragment (`#k=...`) are
  independently addressed and both confirmed to survive (§2). No query string is used
  by this contract today, so nothing to lose there.
- **App/web routing agreement on token representation**: both read the identical raw
  `accessToken` path segment and the identical `#k=...` fragment format
  (`encodeCapsuleKeyForLink`/`decodeCapsuleKeyFromLink`, the same shared `@tc/crypto`
  functions both platforms already call) — confirmed by direct code comparison, not
  assumed identical.
- **Authentication incorrectly imposed on reveal links**: confirmed absent. The mobile
  reveal route (`app/(reveal)/c/[token].tsx`) sits outside both `(app)`'s auth-gated
  group and `(auth)`'s login stack — a PHASE-5.1 decision, re-verified unchanged in this
  session's own reading of the route tree. An App/Universal Link opening this route
  reaches the same unauthenticated screen a manual/custom-scheme link already does;
  nothing about adding the HTTPS scheme changes which route it resolves to.
- **Claiming unrelated paths**: a real, non-hypothetical risk if configured carelessly
  — both `associatedDomains: ["applinks:timelycapsule.com"]` (iOS) and a bare
  `intentFilters` host-only match (Android) would, at the OS-registration level, offer
  to handle **every** path under `timelycapsule.com`, not just `/c/*`. Both platforms'
  own file formats provide the fix: iOS's AASA `paths` array and Android's intent-filter
  `pathPrefix` (used in this spike's own real test, §2) each scope the claim correctly.
  The recommended config in §4/§5 already applies this scoping — this is not a decision
  deferred to implementation, it is stated here as the correct shape.
- **Arbitrary HTTPS capsule tokens received safely**: confirmed. The app performs no
  client-side trust of the URL beyond parsing the token and fragment — every token,
  valid or not, goes through the identical real `GET /r/:token` call and the identical
  masked-404 handling web already has. A malicious or garbage token reaches the same
  honest "No capsule at this link." state this spike's own experiment produced for a
  deliberately nonexistent token (§2).
- **Navigating into an unintended authenticated surface**: confirmed not possible —
  see the authentication-imposition point above. There is no route in this app that a
  `/c/:token` link could resolve to other than the one unauthenticated reveal screen.
- **`outbound_messages.payload` retention** (carried over from E0.2, not re-litigated,
  not newly found): the real announce/resend-invite email payload — including the link
  and its `#k=` fragment — is still durably retained in that table with no purge/TTL,
  confirmed unchanged in this session's own reading of `apps/api/src/modules/email/
  service.ts`. Still an `[OPEN DECISION]` for a founder/security call, still out of
  this spike's scope to fix, still worth repeating so it isn't lost between spikes.

No existing gate was weakened, touched, or reasoned around anywhere in this spike.

## 10. Recommended Implementation Sequence

1. **(Human)** Confirm who can deploy to `timelycapsule.com` and get the two
   `.well-known/` files hosted (assetlinks.json can go out today, real fingerprint
   pending; AASA needs the Apple Team ID first).

4. Update `apps/mobile/app.json` with the real `intentFilters`
   (`pathPrefix: "/c/"`, real fingerprint already hosted) and `associatedDomains`
   (`applinks:timelycapsule.com`), exactly the shapes proposed in §4/§5 — a small,
   mechanical, low-risk change once the above exist.
5. Real-device re-verification on both platforms against the real domain — repeat
   this spike's own §2 methodology, this time for real, closing the one thing this
   spike could not: a physical iOS device with a signed build.
6. Update `plan/PROGRESS.md`'s Open Decision #2 to CLOSED once both platforms are
   confirmed, and only then consider PHASE-5.5 itself complete (not merely spiked).

## 11. Risks

- **Claiming too much of the domain** (§7) if `pathPrefix`/`paths` scoping is dropped
  during a future edit — concrete mitigation already specified, but worth a code-review
  checklist item when this ships for real.
- **Fingerprint drift**: EAS can rotate/regenerate signing credentials; `assetlinks.json`
  must be kept in sync with whatever the *actual* shipped binary is signed with, or
  verification silently fails (matching this session's own explicit reproduction of "a
  reported verification state does not prove a real successful check" — the inverse
  failure mode, a stale fingerprint, is just as invisible without deliberately checking).
- **Toolchain surprise, reproduced twice this session**: `expo run:android` does not
  regenerate the native project from `app.json` once `android/` already exists locally
  — anyone repeating this work must run `expo prebuild` explicitly, or the config change
  silently has no effect while looking like it should. Worth a one-line note wherever
  this ships.
- **Dev-client cold-start is not a reliable proxy for production cold-start** (§3) —
  whoever verifies step 5 above should use a real preview/release build, not a local
  debug dev-client, specifically for the killed-process scenario.

## 12. Experiment Disposal

Every artifact created for this spike was removed before this document was written:
the temporary `intentFilters` block was reverted out of `apps/mobile/app.json`
(confirmed via `git diff` — empty); the temporary local HTTP server, the `localtunnel`
process, the emulator, and the local `apps/api` dev server were all stopped; the two
disposable seeded capsules (a masked-404 test and a real-content test) were deleted
from the dev Postgres database; the local debug keystore itself was not modified (only
read, to extract its already-existing fingerprint) and remains exactly as it was.
`apps/api/src/db/migrate.ts`'s own pre-existing, unrelated modification was never
staged, modified, or touched at any point in this session.

## 14. Explicit Decision

**READY AFTER HUMAN INPUT.**

Not "not ready": the technical mechanism is proven, on real hardware, against this
repo's own real code, for the platform that could be tested. Not "ready to implement"
outright: applying `intentFilters`/`associatedDomains` today, before real hosted
domain files and a real signing fingerprint exist, would produce a change that cannot
be verified, cannot pass domain verification, and would sit in the codebase as
unverifiable and therefore untrustworthy — exactly the "STATE_APPROVED without ever
fetching" trap this spike (and E0.2 before it) found real evidence against trusting.
The correct next action is the human/external sequence in §10, not a mobile PR.
