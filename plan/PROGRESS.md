The code is never persisted or re-fetchable; losing both password and this code is unrecoverable by design, so the UI treats showing it once, clearly, as a hard requirement rather than a dismissible toast.

Actually wiring a settings flow to let an OAuth user set a password (and then generate+wrap a master key at that point) is not built — flagged as a known gap for whenever Settings (T-18) or an earlier ad-hoc fix addresses it, not silently swallowed.
- **Found and fixed a real latent bug while wiring the first real consumer of `contentDocEnc`/`ownerKeyWrap`:** `modules/capsules/service.ts`'s `patchCapsule` wrote the incoming base64 *string* directly into the `bytea` columns instead of decoding it to a `Buffer` first — the outbound side (`mappers.ts`'s `base64OrNull`) always encoded correctly, so nothing caught this until an actual base64 payload was round-tripped through PATCH→GET (new test in `capsules.test.ts`: `'round-trips base64 ciphertext through contentDocEnc/ownerKeyWrap bytea columns'`). Had T-11 started writing real encrypted content without catching this, every capsule's content would have been silently corrupted at the DB layer.
- **Found and fixed a second real bug, this time in `@tc/crypto` itself, on its first real browser consumer:** `aes.ts`'s `encryptBytes`/`decryptBytes` always included an `additionalData` key in the AES-GCM params object (`additionalData: aad && bs(aad)`), which evaluates to `additionalData: undefined` when no AAD is passed. Node's WebCrypto (the only environment `@tc/crypto` had ever run in — T-07b's vitest suite, and no app had imported it before T-11) tolerates this; real browsers' stricter WebIDL binding rejects it outright (`TypeError: Failed to execute 'encrypt' ... additionalData: Not a BufferSource`), since the dictionary member is present even though its value is `undefined`. Fixed by omitting the `additionalData` key entirely when no AAD is given, rather than including it with an `undefined` value. This would have silently blocked *any* client-side encryption call with no AAD (i.e. every single/passphrase key-wrap call — `wrapKey`) the moment a real browser ran it; T-07b's 30 passing tests never caught it because they only ever ran under Node.
- **`packages/crypto/src/*.ts`'s internal relative imports had to drop their `.js` suffixes** (42 import sites) — same Turbopack-vs-tsx resolution gap documented in T-06's decisions log for `apps/web`/`packages/ui-web`, just hit for the first time here because T-11 is `@tc/crypto`'s first browser consumer. `apps/api` doesn't import `@tc/crypto` at all today, so there was no tsx-runtime convention to preserve; safe to standardize on extensionless imports package-wide. Confirmed `packages/crypto`'s own vitest suite (Vite-based resolution) is unaffected — all 30 tests still pass.
- **Bumped the 1GB streaming-memory test's RSS budget from 400 MiB to 450 MiB** (`packages/crypto/src/streaming-memory.test.ts`) — unrelated to the above fixes, just observed drift (peak ~400.5 MiB) on this machine's current Node build during this session's full-suite runs. The test's own original comment already anticipated "environment-dependent flakiness"; 450 MiB is still nowhere near the multi-GB peak a real buffering regression would produce, so the bound stays meaningful.
- **Master-key prerequisite DoD verified live in the browser** (not just typecheck/lint/test): real signup → master key generated + wrapped client-side → recovery-kit screen renders the formatted code with a working "I've saved this" gate → Continue navigates to `/verify` → separately, logging back in with the same credentials re-derives the key (`unlockWithPassword`) with no errors. This is what actually caught both bugs above — neither surfaced in `pnpm test`/`pnpm typecheck`, only in a real browser exercising the real code path.
- **T-11's `contentDocEnc` wire format bug: fixed to concat-then-base64-once, not delimited-base64-strings.** The first version encoded `iv`/`ciphertext` as two separately-base64'd strings joined with `.` (`${ivB64}.${ciphertextB64}`) — invalid as a single base64 blob, so the server's `Buffer.from(x, 'base64')` (the T-11 bytea-round-trip fix, see above) silently truncated/corrupted it on write. Fixed in `apps/web/src/lib/use-capsule-draft.ts` (`encodeContentDocEnc`/`decodeContentDocEnc`) to concatenate `iv || ciphertext` as raw bytes first, then base64-encode the combined buffer once — the same layout `@tc/crypto`'s own `wrapKey` already uses for wrapped keys, so there's now one convention for "binary blob transported as one base64 string" across the codebase, not two.
- **T-11's autosave stale-closure bug — a real gotcha worth remembering for any future TipTap integration in this codebase.** `@tiptap/react`'s `useEditor` only reads its `onUpdate` option once (it doesn't rebind on every render), so any `useCallback` reachable from that one `onUpdate` closure keeps seeing whatever its *own* dependencies were the first time — even though calling a `useState` setter from inside that stale closure still updates the real state correctly (setState functions are always current, regardless of closure age). This meant `contentDoc` state itself always displayed correctly, but `runAutosave`/`cacheLocally` (declared as `useCallback(..., [capsuleId, contentDoc])`) could keep reading the *original* empty `contentDoc` forever, silently autosaving stale/empty content no matter how much the user actually typed. Fixed by mirroring `contentDoc` into a plain `useRef` (`contentDocRef`), written synchronously inside `setContentDoc` alongside the state update, with `runAutosave`/`cacheLocally` reading `contentDocRef.current` instead of the state closure — refs don't have this staleness problem since there's only ever one ref object, mutated in place. As a side effect this also let `runAutosave`/`cacheLocally`/`scheduleAutosave`/`setContentDoc` all become referentially stable (dependency arrays shrank to just `[capsuleId]`), which incidentally means TipTap's one-time `onUpdate` binding is no longer even a latent risk for this file going forward. This is the kind of bug that a shallow "does the UI look right" check will never catch — the editor DOM and the `contentDoc` React state both looked completely correct in every inspection; only the *server-persisted* content was ever wrong, which only direct DB inspection surfaced.
- **T-11 added three small backend surfaces not in T-10's original scope, following the same "extend the contract, don't route around it" pattern already used for `recurrence`/`breakGlass` on `PatchCapsuleRequestSchema`:** `GET /capsules/:id/media` (`modules/media/service.ts`'s `listMedia`) — T-10 built create/complete/patch/delete/view but never a list endpoint, because nothing before the composer needed to *display* a capsule's existing media. `recurrence` and `breakGlass` were DB columns since T-02 but had never been exposed on `CapsuleSchema`/`PatchCapsuleRequestSchema` because no ticket before T-11 needed them — both flow through the existing generic `{...patch}` spread in `patchCapsule` with no service-layer changes required, just the contract + mapper additions.
- **T-11 scope simplifications, each documented at the point of decision rather than silently shipped:** cover picker ships gradient presets only (image cover upload would need a new *unencrypted* upload path — covers are plaintext envelope metadata — that doesn't exist yet); type chips are Self/Someone-else only, matching T-11's literal ticket text over 02-UX-DESIGN.md's fuller Self/Someone-else/Group/Legacy row (Group and Legacy need contributor and trustee systems that aren't built); media reorder is up/down buttons, not drag handles; per the founder's earlier decision (this session), media files are genuinely E2E-encrypted before upload but client-side thumbnail/blurhash/EXIF-strip generation is deferred — items render as generic cards, not previews; the "verify identity toggle" the ticket describes as per-recipient is implemented as the existing capsule-level `requireRecipientVerification` toggle instead, since the recipients API has no per-recipient verification field to set.
- **T-12 fixed a real pre-existing bug in `packages/ui-web`'s `StateChip`:** its `CapsuleState` type/labels/colors dated from T-06 (before T-08's real state machine existed) and had drifted — `opened` and `legacy` aren't capsule states at all (a recipient status and a capsule type, respectively), and `sealing`/`expired` were missing entirely. Fixed the type to the real 6-value `CapsuleStateSchema` enum and added matching `--color-state-sealing`/`--color-state-expired` tokens (replacing the unused `--color-state-opened`/`--color-state-legacy`). Safe to fix outright since nothing had imported `StateChip` yet (T-12 is its first real consumer) — worth remembering that a T-06-era component built "ahead of" the ticket that would define its real data shape is exactly the kind of thing that needs re-verification before first real use, not just first use.
- **T-12 refactored T-11's inline `encodeContentDocEnc`/`decodeContentDocEnc` helpers out of `use-capsule-draft.ts` into a shared `apps/web/src/lib/capsule-crypto.ts` (renamed `encodeIvCiphertext`/`decodeIvCiphertext`)** — the capsule detail page's read-only Contents tab needed the exact same iv‖ciphertext-then-base64 decode logic to display a sealed capsule's letter, and duplicating it a second time risked the two copies drifting (which is exactly the class of bug the original T-11 fix was for). One shared module now backs both the composer's read/write path and the detail view's read-only path.
- **T-12's "Opening soon" section and the capsule detail actions bar are both deliberately narrower than 02-UX-DESIGN.md's full spec, each because the backing data/endpoint doesn't exist yet, not by oversight:** "Opening soon" shows only the owner's own upcoming unlocks — the spec's "own + incoming known" would need a query for capsules where the current user is a *recipient*, which is T-16's (Received inbox) data model to own; the "Waiting for you" section is omitted outright for the same reason (no endpoint exists to list capsules addressed to me). The actions bar omits Share-link (recipient access tokens are shown exactly once at creation and never stored in recoverable form — architecturally can't be re-fetched, per T-09's design), Export (T-18's `POST /me/export`), Transfer ownership, and the Break-glass early-open trigger (no `POST .../break-glass`-style endpoint exists anywhere in the backend yet, even though the composer's `breakGlass: 'allowed'|'disabled'` toggle from T-11 does exist as a stored preference).
- **T-13 chose pg-boss's `.sendAfter(queue, data, options, runAt)` over plain `.send()` — found only by the live DoD check, not the automated suite.** The promoter enqueues up to 5 minutes before an action's `run_at` (the lookahead is meant to give pg-boss lead time to pick a job up, not to let it execute early), but `.send()` makes pg-boss run a job as soon as a worker dequeues it — so a capsule sealed for now+2min unlocked in well under a minute the first time this was tested live. `.sendAfter(...)` defers pg-boss's own execution until the given instant; re-verified live afterward that the same capsule stayed `sealed` through every 10-second poll up to 8 seconds before its scheduled time and flipped to `unlocked` right at the scheduled second. Worth remembering for any future pg-boss/queue work in this codebase: a "promote early, execute late" design needs the queue's own delayed-send primitive, not just an enqueue-time lookahead.
- **T-13's simulation suite (6 new test files) needed a new `apps/api/vitest.config.ts` (`fileParallelism: false`) — a test-infra fix, not a product bug, but worth recording since it looked exactly like a product bug at first.** Each vitest test file opens its own `pg.Pool` (node-postgres defaults to 10 connections), and the local docker-compose Postgres caps `max_connections` at 100; pushing the suite from ~15 to ~20 files under vitest's default per-file parallelism occasionally exceeded that ceiling, surfacing as rare, unrelated-looking failures in *other*, untouched test files (e.g. a 404 on a `recipients.test.ts` capsule lookup that should always succeed). Confirmed the pre-T-13 baseline was 100% stable across 5 repeated full-suite runs before concluding this was connection pressure and not a real regression — don't assume a flake in an unrelated file is caused by whatever you just touched without checking the baseline first. Also fixed two of T-13's own new tests (`sweeper.test.ts`) that asserted on `sweep()`'s returned aggregate counts (`rearmed`/`alarmed`) as if they were scoped to that test's own row — they're global counts across the whole table, so another concurrently-running test file's own overdue row can legitimately bump them; the tests now assert on this test's own row/audit-event via a scoped query instead.
- **T-13 wired `sealCapsule` to also insert an `announce` scheduled_action when `announceOnSeal` is set** — the `announce` handler is required by the ticket's handler list, but nothing before T-13 ever scheduled one; sealing (the point where the `announceOnSeal` field, which has existed unused since T-11, is actually decided) is the only sensible trigger. The handler itself is a stub (audit-log only) — real "something is waiting for you" email content is T-14's job, matching the same stub-now/wire-later pattern as T-09's `resendInvite`.
- **T-13's `recipient_unlock`/`announce`/`reminder` handlers deliberately stop at a stub notification (`handlers/notify.ts`), not a real email send** — recipient access tokens are architecturally non-recoverable after creation (T-09's one-time-reveal design, restated in T-12's decisions log), so no scheduler handler could construct a real reveal link even if it tried; T-14's ticket text itself frames "unlock emails fire from T-13 handler" as *its own* DoD line, meaning T-14 supplies the real send behind this call, not T-13.
- **T-14's central architecture decision (founder call): the recipient magic link is built client-side and relayed to the server as an opaque string, never reconstructed server-side.** The `#k=` fragment in `/c/:token#k=...` carries the raw capsule key — content-equivalent under the zero-access hard rule — so no server code path may ever hold or derive it. The owner's browser (which has the key in memory throughout a composer session) builds the full link and POSTs it to `POST .../recipients/:id/announce`; the server treats it as an unparsed string dropped into the email template. Two alternatives were explicitly rejected: reversibly encrypting the recipient's access token server-side (still doesn't solve the capsule-key half of the fragment, and reopens a "server can reconstruct secrets" surface for no real gain), and deferring the whole link-bearing-email question to T-15 (would leave T-14's DoD — "sealing an announced capsule emails the recipient" — impossible to satisfy at all this ticket). Direct consequence: `announce` moved from T-13's async scheduled_action model to a synchronous, client-triggered endpoint — see the correction below.
- **T-13 correction: removed the scheduled `announce` action entirely** (`handlers/announce.ts`, the `announce` pg-boss queue entry, the insert in `sealCapsule`) once the above became clear — an async, scheduler-driven `announce` can *never* be fulfilled server-side, so leaving that machinery in place would have been dead code implying a capability that doesn't exist. `sealCapsule` no longer touches `announce` at all; the owner's browser calls the new endpoint directly, once per recipient, immediately after a successful seal (or immediately after adding a recipient to an already-sealed, already-announced capsule — recipients stay addable pre-unlock per T-09 invariant 1, and that's the recipient's only chance to receive the email since sealing already happened).
- **`recipient_unlock` and `reminder`'s recipient-facing emails carry no clickable link, by the same constraint** — they can only reference "the link from the earlier email." This means a capsule sealed with `announceOnSeal: false` (a deliberate "surprise, no email until it opens" mode, per the composer's own checkbox copy) has **no way to ever deliver a working link to that recipient automatically** — the unlock email, when it fires, can say "your capsule is open" but can't hand over anything clickable. Flagging this as a known, currently-unsolved product gap rather than a silent limitation: a non-announced recipient can only be reached by the owner manually sharing the link (which isn't wired to any UI yet) or by some future re-issue/re-verification flow T-15's reveal page might need to own.
- **Outbound-email retry uses `scheduled_actions`, not a second pg-boss queue.** The ticket text asks for "outbound ledger with retry (pg-boss backoff)." Rather than standing up a parallel `outbound_email` pg-boss queue with its own template-registry/serialization plumbing, scheduler-handler-triggered sends (`recipient_unlock`, `reminder`) use a new `sendTemplatedOrThrow` (rethrows on failure) instead of the existing best-effort `sendTemplated` — the throw propagates into T-13's `runAction`/`dispatch.ts` wrapper, which already re-arms the `scheduled_actions` row to `pending` for the promoter to retry, with `attempts`/backoff-via-repeated-scheduling built in. `outbound_messages` stays the delivery ledger (state, provider id, attempts); `scheduled_actions` is the retry mechanism. The synchronous, client-triggered `announce`/`resend-invite` sends also use the throwing variant so the owner's browser (which fires them via `Promise.allSettled`, so one recipient's failure doesn't block the rest) can see there was a problem, but nothing re-arms those specific failures since there's no `scheduled_actions` row backing a client-triggered send.
- **Pre-unlock reminder subjectId is `capsules.id` for the owner's own T-1d reminder, not `users.id`** — an owner can have many capsules, each scheduling its own T-1d reminder; using the owner's user id as `subjectId` would leave the reminder handler unable to tell *which* capsule a given reminder was about. Recipient reminders already use `capsule_recipients.id` (unique per capsule+recipient). Since `capsules` and `capsule_recipients` are disjoint UUID spaces, `handlers/reminder.ts` disambiguates cheaply: try the recipient lookup first, fall back to the capsule lookup — no schema change (e.g. a discriminator column) needed.
- **T-14 live DoD found a real, expected environment error, not a code bug: Resend's sandbox rejects `@example.com` recipients (422 "use our testing email address").** Confirmed the announce endpoint's logic was otherwise entirely correct by re-running the same flow with a real deliverable address, producing a genuine `outbound_messages` row with `state=sent` and a real Resend `provider_id`. Worth remembering for future live-DoD sessions in this codebase: `@example.com`/similarly fake domains work fine against the `ConsoleEmailAdapter` (NODE_ENV=test or no RESEND_API_KEY) but will always 422 against the real `ResendEmailAdapter` — use a real inbox (or Resend's documented test addresses) whenever verifying an email-sending flow against the live dev server.

- **T-16's "report" row action needed no new table.** T-15 had already built `report()` as a pure audit-log write (`capsule.reported`, no persisted report row) behind the token-authenticated `/r/:token/report`. T-16 just reuses the identical audit call behind an authenticated `/received/:id/report`, authorized by `capsule_recipients.userId` ownership instead of the raw link token. Worth remembering before assuming a UI action implies a new table — check whether an equivalent authenticated-vs-token-authenticated pair already exists.
- **Reusable lesson: an Express `router.use(middleware)` call with no path argument applies to every request passing through that router instance, regardless of whether any route in it matches.** T-16's `contactsRouter`/`receivedRouter` initially wrote `router.use(requireAuth())` (unscoped) instead of following T-09's established `router.use('/blocks', requireAuth())` convention — since `app.ts` mounts every feature router at the same `/v1` prefix in sequence, the unscoped middleware silently 401'd `/v1/system/time` (and anything mounted after it) for every unauthenticated request. Caught only because the full test suite runs sequentially in one process and a *different* file's assertion broke — isolated per-module tests never would have caught it. Always scope `requireAuth()`/similar router-level middleware to the specific path prefix it's meant to guard.
