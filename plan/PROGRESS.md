- **`idempotency_keys` is a new table**, not in the original 03 §13 schema list — T-03's ticket text explicitly calls for "table-backed" idempotency, and no such table existed. Uniqueness on `(key, method, path, userId)`; see the known gap noted in `apps/api/CONVENTIONS.md` about anonymous requests before T-04 auth lands.
- **Idempotency and rate-limiting are per-route opt-ins, not globally mounted** in `app.ts`. There are no real side-effecting feature routes yet (T-04 adds the first), so global wiring would have nothing real to prove; `CONVENTIONS.md` documents the middleware order (`rateLimit → idempotency → validate → handler`) for T-04 onward to follow.
- **Module-boundary ESLint rule needed `eslint-import-resolver-typescript`**, undocumented as a prerequisite anywhere obvious — without it, `eslint-plugin-boundaries` silently never fires on this repo's `.js`-suffixed relative imports (they fail to resolve to the real `.ts` files, so files never get classified as being inside a module). Caught by building a real throwaway two-module violation and confirming the rule actually caught it before trusting the config — worth remembering as a general practice for any lint-rule-as-architecture-guardrail work.
- **T-04 refresh-token reuse detection uses the `sessions` row itself as the "family,"** not a separate token-family table: added `sessions.previous_refresh_token_hash` (one generation of lookback only). A refresh matching the *previous* hash means the token was already rotated out and is being replayed — the whole session is revoked immediately. Simpler than a full token-lineage table and sufficient for the ticket's DoD (a reuse test that also proves the legitimately-rotated token dies with it).
- **JWT signing key: RS256 via a real asymmetric keypair (`jose`, PKCS8/SPKI PEM, base64'd into env vars `JWT_PRIVATE_KEY_B64`/`JWT_PUBLIC_KEY_B64`)**, generated locally with `apps/api/scripts/generate-jwt-keys.mjs`. Under `NODE_ENV=test` (vitest's default), an ephemeral keypair is generated in memory instead — so CI needs no JWT secrets and `pnpm test` works with zero setup. Real deployments (T-19+) must set the two env vars from a keypair that isn't the one checked into a dev's local `.env`.
- **Email OTP codes are two different shapes for two different reasons:** verify-email uses a 6-digit numeric code scoped to a known `userId` (the signup response already returns tokens, so the caller is authenticated) with a 5-wrong-guess burn limit on the `attempts` column; password reset uses a 32-byte opaque token looked up by hash alone with no userId (the requester isn't authenticated yet) — long enough that brute-forcing it isn't a realistic concern, so no attempt-limiting needed there. Both live in one new `email_otp_codes` table (`otp_purpose` enum) rather than two tables, since the shape (hash + expiry + used-at) is identical.
- **Both OTP flows log the raw code via the shared `logger` (pino) and never include it in any HTTP response body** — this *is* "log to console until T-07" from the ticket text, not a placeholder for it. Integration tests get the raw code by calling the service functions (`issueEmailVerifyCode`/`issuePasswordResetToken`) directly rather than parsing a response body, which will keep working unchanged once T-07 swaps the delivery side for real email.
- **Password reset revokes every active session for that user** (not just the one that requested it) — not explicitly required by the ticket text, but a direct application of plan §17 threat #3 (account takeover) and standard practice: a password reset is exactly the moment you want every other logged-in device (including a possible attacker's) forced to re-authenticate.
- **New-device detection (T-04's "stub") logs a structured `login_new_device` event via pino** and does nothing else — no email, no `audit_events` row. The real notification is explicitly T-07's job once the email adapter exists; wiring it to `audit_events` instead was considered but skipped since the ticket only asked for a stub and audit-log semantics for security events haven't been decided yet.
- **Google OAuth client setup (2026-07-24):** Web client ID obtained and in use (`GOOGLE_OAUTH_WEB_CLIENT_ID`, see `.env.example`). iOS bundle ID / Android package name set to `com.timelycapsule.app` in `apps/mobile/app.json` (added ahead of T-23 while doing this setup, since Android's OAuth client needs the package name + a SHA-1 anyway). A standard Android **debug** keystore was generated at `~/.android/debug.keystore` (default alias/password `androiddebugkey`/`android`) purely to extract a SHA-1 fingerprint for the Android OAuth client — this is dev-only; the release-signing keystore `eas build` produces later (T-23+) will need its own SHA-1 added to the same Android client as a second entry.
- **T-05 verifies Google idTokens with `jose`'s `createRemoteJWKSet`, not `google-auth-library`** — one fewer dependency, and consistent with `jose` already handling our own JWT signing/verification (T-04). `verifyGoogleIdToken`'s JWKS resolver is an injectable parameter specifically so tests never make a live network call to Google — they verify against a locally-generated keypair instead. Only the Web client ID is checked as `audience` right now; iOS/Android client IDs (now created, see above) aren't validated yet since no mobile client exists to send them — revisit the audience check when T-23 adds native Google Sign-In.
- **Ghost-claim lives in one shared function (`ghost-claim.ts`) called from two places:** T-04's password `/auth/verify-email` completion and T-05's Google OAuth flow. The ticket text ("on any signup/OAuth with verified email matching `capsule_recipients.email`") was written under T-05 but describes a condition — "email became verified" — that password signup can also reach; splitting the logic per-ticket would have left password-signup users permanently unable to ghost-claim.
- **A Google account with `email_verified: false` is rejected outright**, not silently allowed through as an unlinked/unverified account. Google marks an email unverified in rare cases (e.g. some Workspace configs); since ghost-claim and auto-linking both act on the trust that this email belongs to this person, honoring an unverified email here would let someone claim another person's pending capsule recipient rows by registering a look-alike Google account.
- **Tailwind v4's automatic content detection does not reach sibling workspace packages.** `apps/web/src/app/globals.css` needed an explicit `@source "../../../../packages/ui-web/src";` — without it, Tailwind only scans within `apps/web`'s own directory tree, so any utility class used *only* inside `@tc/ui-web` (not coincidentally repeated verbatim in an `apps/web` file) silently never gets generated. This produced a genuinely confusing bug during T-06 browser verification: components rendered with *some* styling (whichever classes happened to also appear literally in an `apps/web` page file) but not others (e.g. `h-10`, `px-3`, fixed sizes/padding never used elsewhere) — looked like a partial Tailwind failure rather than a missing scan root. Confirmed via `document.styleSheets` walk + `getBoundingClientRect`, not by trusting the rendered screenshot alone. Anyone adding a second shared UI package later needs its own `@source` line too.
- **`apps/web` (and `@tc/ui-web`, since it's consumed by webpack/Turbopack, not `tsx`) must NOT use `.js`-suffixed relative imports** — that's `apps/api`'s convention (Node ESM via `tsx`, resolved through `moduleResolution: Bundler` in tsc but real files at runtime need the literal extension). Next.js's Turbopack bundler does not resolve `.js`-suffixed imports back to `.tsx`/`.ts` source the way `tsx`/tsc-in-bundler-mode do, and fails the build with `Module not found`. `apps/web`'s and `packages/ui-web`'s own relative imports are extensionless; only `apps/api`'s modules use the `.js` suffix. Caught at `pnpm build` time, not lint/typecheck (both passed with the `.js` suffix in place — this is a bundler-vs-tsc resolution gap, not a type error).
- **`AuthContext`'s initial "am I logged in" check uses React Query's `useQuery`, not a plain `useEffect` + `setState`.** The obvious first draft (fetch `/me` in a `useEffect`, `setLoading(false)` in `.finally`) is flagged by the `react-hooks/set-state-in-effect` ESLint rule (cascading-render risk) — fixed by moving the bootstrap into `useQuery({ queryKey: ['me'], enabled: hasTokens })`, which also means the `QueryClientProvider` wired up for "the React Query requirement" is now actually load-bearing rather than present-but-unused.
- **Google Sign-In on web is wired for real, not stubbed** — `GoogleSignInButton` loads the Identity Services script client-side and calls the already-built T-05 `/auth/oauth/google` endpoint. Apple Sign-In is intentionally absent from both auth screens (not just disabled): plan/05 §T-04-human-setup explicitly defers Apple Sign-In to T-28 (needs a paid Apple Developer account), so there's nothing to render yet.
- **Password strength meter is a small heuristic (length + character-class variety), not `zxcvbn`** — avoids pulling in zxcvbn's ~800KB wordlist for inline feedback that's advisory only; the real gate is server-side `PasswordSchema.min(8)` in `@tc/contracts`. Revisit if product wants zxcvbn's smarter entropy estimate.
- **Password reset (`/reset`) is one route serving two states based on a `?token=` query param**, not two separate pages — matches the UX spec naming it as a single `/reset` screen while the backend already has distinct `forgot`/`reset` endpoints.
- **Templates use `react-email`, not MJML** (the ticket allowed either) — `@react-email/render`'s `render(node)` / `render(node, {plainText:true})` gives both the HTML and the required plain-text alt from one JSX source, with no separate build step or CLI needed, which MJML would have required. `apps/api/tsconfig.json` gained `"jsx": "react-jsx"` and `react`/`react-dom`/`@types/react*` purely to support this — the templates are the only JSX in the whole API. **`react` had to be pinned to the exact same version as `react-dom` (19.2.4)** — installing `react` fresh pulled 19.2.8 while `react-dom` (already present, pinned by `resend`'s peer deps) stayed at 19.2.4, and React throws `Incompatible React versions` at render time (not at typecheck/lint) on any mismatch. Anyone bumping either package in `apps/api` needs to bump both together.

Same pattern as T-04's JWT-keys/test-mode guard.
- **Resend's webhook secret format is `whsec_<base64>`, not an arbitrary string** — `svix`'s `Webhook` constructor base64-decodes everything after the prefix, so an arbitrary placeholder throws (as an uncaught error, surfacing as a 500, not the intended 401) rather than failing signature verification cleanly. `RESEND_WEBHOOK_SECRET` in `.env` is a properly-formatted placeholder (`whsec_` + random 32 bytes base64) generated locally — it isn't a real registered webhook secret yet, since Resend can't deliver to `localhost`. Register the real webhook (and swap this value) once the API has a public URL, per `.env.example`'s note.

This proves the whole pipeline end-to-end (template render → adapter → Resend → SES → delivered) without needing to read anyone's actual inbox; DKIM/SPF pass is implied by Resend accepting and delivering from a domain it verified itself, though the user should still eyeball the email once for a final human check.
